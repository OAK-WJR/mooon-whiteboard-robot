# 顶部板的无线供电策略

C6 审查固件已把无线启动与电池接口电压联系起来，保留 USB 诊断、下载与自动恢复。本次不增加板上器件，不改变现有三角形板框或底板接口。电压是现有 ADC 分压的诊断读数，整板供电及实物无线性能仍未合格。

## 运行方式

| 条件 | 固件行为 |
| --- | --- |
| 上电／复位后 | UART0 和电压采样先工作；不初始化蓝牙或 Wi-Fi。USB `status`、`rails` 和重启可用 |
| 有效电池读数连续满足条件 | 读数处于 6.5–8.8V，连续采样跨度至少 1 秒，相邻采样开始时刻相差不超过 150ms；看门狗可用且没有待处理重启时，才启动无线 |
| 启动无线 | 先撤销已有控制租约；每次启动周期仅初始化一次 BLE，有有效密钥和 SSID 时也启动 Wi-Fi；客户端重新取得控制租约 |
| 无线已启动 | 有效读数在 6.0–8.8V 范围内可继续运行；启动与保持阈值分开，避免边界反复切换 |
| 运行中电池读数越界、ADC 失败／过期或 GPIO 安全初始化失效 | 在处理下一批通信数据之前撤销控制、请求安全输出，并执行软件复位；下一次启动重新判断供电条件 |
| 无线初始化失败 | 报告 `init_failed`，不在同一启动周期反复初始化；USB 诊断及用户／AI 重启入口保留。部分 SDK 初始化可能已完成，仍持续监控供电 |
| 应用重启正在等待发送回复 | 继续电压采样；供电正常时保留原回复等待流程，供电失效时优先自动复位，回复可能未发完 |

软件复位会重新执行启动程序，并复位 Wi-Fi、BT、UART0 等指定外设；它不是切断 PCB 电源。独立 CH343 的 USB 连接不由 ESP32 的软件直接复位，但桥接器及串口重新连接行为仍需实板验证。[乐鑫 `esp_restart()` 说明](https://docs.espressif.com/projects/esp-idf/en/v5.5.2/esp32c6/api-reference/system/misc_system_api.html#_CPPv411esp_restartv)。

本项目安装的 BLE 库在初始化中等待主机同步，并有额外 200ms 延时。这里使用一次初始化及软件复位切换模式，不反复调用 `BLEDevice::deinit` 重建异步对象。任务看门狗在无线初始化之前已经注册；初始化返回后立即复查采样。SDK 阻塞期间没有连续电压采样，因此不能据此保证拔电池后的最大关断延迟或 USB 瞬态电流。[乐鑫 BLE 实现](https://github.com/espressif/arduino-esp32/blob/master/libraries/BLE/src/BLEDevice.cpp)。本地实际编译版本和哈希见下方验证记录。

## USB 可读诊断

```sh
.venv/bin/python scripts/robot_control.py --usb PORT --usb-kind ch343g rails
```

原电压报告增加 `wireless_power_state`、`wireless_start_attempted`、`previous_radio_power_reset`。前两项区分等待电压、确认中、启动中、运行和初始化失败；“已尝试启动”不代表无线连接成功。最后一项使用 RTC no-init 的标记及反码，只在软件复位原因匹配时接受，并在本次启动消费清除，供 AI 识别前一次自动供电复位。它不写 Flash、不保证完整掉电后保留，也不是详细故障波形记录。

## 验证与未完成项

生产主循环测试覆盖 USB 单独供电、缺少 ADC 校准、看门狗不可用、电压波动后重新计时、运行中断电／ADC 故障／过期／GPIO 故障、初始化期间断电、四种 SDK 初始化失败，以及复位标记的接受和拒绝。纯策略测试还覆盖时间回绕和重复使用旧样本。原 USB/Wi-Fi/BLE 重启、认证、分片及共享 R3 回归保留；完整软件计数和编译结果见[软件报告](firmware_verification/report.json)、[本次来源与范围](verification/wireless_power.json)。所有故障输入和复位都是测试替身，尚未证明实物 RTC 保持或无线链路性能。

6.5V／6.0V／8.8V 是针对当前 2S 电池接口的**软件读数阈值**，外部分压未逐板校准，不是电芯保护阈值、USB 电流额度或 6V 稳压保证。单个 ADC 卡在合理数值仍可能漏检；输入保护、ADC 掉电行为、USB 枚举与挂起、插拔和浪涌、射频／电源瞬态、整板布线及完整成本仍需完成。运动保持禁用，不能称为整板稳定性验证通过。
